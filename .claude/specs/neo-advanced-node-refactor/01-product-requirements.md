## 1. 执行摘要

### 1.1 项目愿景

将 Neo 区块链节点从传统单体架构演进为**云原生、高性能、模块化**的下一代区块链基础设施，通过技术栈现代化实现 **10倍性能提升**，同时保持 100% 向后兼容。

### 1.2 核心目标

| 维度 | 当前状态 | 目标状态 | 提升倍数 |
|------|----------|----------|----------|
| **TPS** | 1,000 | 10,000+ | 10x |
| **区块确认时间** | 15秒 | 3秒 | 5x |
| **同步速度** | 1,000 blocks/s | 10,000+ blocks/s | 10x |
| **启动时间** | 30秒 | <5秒 | 6x |
| **内存占用** | 2GB | <1GB | 2x |

### 1.3 技术栈迁移

| 层次 | 当前技术 | 目标技术 | 优势 |
|------|----------|----------|------|
| 运行时 | .NET 8 | .NET 10 + NativeAOT | 启动更快，内存更少 |
| Actor 模型 | Akka.NET | Microsoft Orleans | 更好的云原生支持 |
| 存储引擎 | LevelDB/RocksDB | RocksDB + LMDB | 读性能优化 |
| 序列化 | 自定义 | MessagePack | 零拷贝，更快 |
| 网络 | TCP | QUIC + TCP双栈 | 多路复用，低延迟 |
| API | JSON-RPC | gRPC + GraphQL | 类型安全，流式传输 |

## 2. 问题陈述

### 2.1 当前架构痛点

#### 技术债务
- **Akka.NET 深度耦合**: 5个核心 Actor 与业务逻辑强绑定
- **循环依赖**: Network ↔ SmartContract ↔ Ledger ↔ VM 形成复杂依赖网
- **序列化开销**: 自定义 ISerializable 接口缺乏零拷贝优化
- **TCP 单协议栈**: 无法利用 QUIC 的多路复用和低延迟特性

#### 性能瓶颈
- **Actor 消息开销**: Akka.NET 消息传递延迟 ~1-2ms
- **同步 I/O**: LevelDB/RocksDB 读写阻塞主线程
- **JIT 启动延迟**: 冷启动需要 30秒 JIT 编译
- **内存碎片**: 长时间运行后内存占用达 2GB+

## 3. 范围定义

### 3.1 项目范围 (In Scope)

#### Phase 1: 基础设施现代化 (6个月)
- Orleans 迁移: 替换 Akka.NET Actor 模型
- NativeAOT 编译: 启用 .NET 10 原生编译
- MessagePack 序列化: 替换自定义序列化

#### Phase 2: 网络与存储优化 (6个月)
- QUIC 协议栈: 实现 QUIC + TCP 双栈支持
- libp2p 集成: 增强 P2P 网络能力
- LMDB 读缓存: 优化热数据读取

#### Phase 3: API 与可观测性 (6个月)
- gRPC API: 类型安全的 RPC 接口
- GraphQL 查询: 灵活的数据查询层
- OpenTelemetry: 分布式追踪

### 3.2 不在范围内 (Out of Scope)

- 共识算法修改: dBFT 2.0 保持不变
- VM 指令集变更: Neo.VM 保持兼容
- 协议层破坏性变更: 网络协议保持兼容
